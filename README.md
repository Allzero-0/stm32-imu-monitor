# STM32F103 + MPU6050 姿态采集与上位机监控系统

> 一个从寄存器写起、能跑、能演示、能讲清楚的嵌入式小项目。  
> 下位机 200Hz 采样、100Hz 通过串口上传二进制帧；上位机实时显示姿态立方体、  
> 加速度/角速度/ADC 曲线，支持一键 CSV 记录。

```
STM32F103C8T6 ──I2C──> MPU6050（六轴）
       │
       ├──ADC+DMA──> 外部模拟量 ×2 + 芯片内部温度
       │
    USART1 115200
       │
   二进制帧(CRC8)
       │
   Python 上位机 ──> 浏览器实时曲线 / 3D 姿态 / CSV
```

---

## 一、它到底做了什么

| 环节    | 实现                        | 关键技术点                        |
| ----- | ------------------------- | ---------------------------- |
| 传感器采集 | GPIO 模拟 I2C 突发读 14 字节     | 避开 STM32F1 硬件 I2C 死锁问题；带总线恢复 |
| 模拟量采集 | ADC1 三通道扫描 + DMA 循环搬运     | CPU 零参与，随时读最新值               |
| 采样节拍  | TIM2 200Hz 更新中断           | 中断只置标志，重活放主循环                |
| 姿态解算  | 加速度/陀螺仪互补滤波               | 理解两类传感器误差特性                  |
| 数据传输  | 自定义二进制帧 + CRC8 + 序号 + 时间戳 | 带宽占用仅为 ASCII 方案的 1/3         |
| 上位机   | Python + 浏览器 Canvas       | 无 GUI 依赖，跨平台，可远程看            |
| 可靠性   | 丢帧统计、CRC 错误计数、I2C 自动重初始化  | 能量化地说明系统跑得怎么样                |

**没有用任何厂商库**（无 HAL、无 CMSIS 库、无 STM32Cube），  
RCC/GPIO/USART/ADC/DMA/TIM/I2C 全部是直接操作寄存器，启动文件、链接脚本、  
向量表都是手写的。这是刻意的选择 —— 面试时能说清每一个寄存器在干什么。

**MPU6050 → STM32**

| MPU6050 | STM32   | 备注                      |
| ------- | ------- | ----------------------- |

| USB-TTL | STM32                |
| ------- | -------------------- |

| RXD     | **PA9** (USART1_TX)  |
| GND     | GND                  |

**ST-Link → STM32**

| ST-Link | STM32 |
| ------- | ----- |
| SWDIO   | PA13  |
| SWCLK   | PA14  |
| GND     | GND   |
| 3.3V    | 3.3V  |

**外部模拟量（可选）**

| 信号              | 引脚                |
| --------------- | ----------------- |

## 三、快速开始

### 1. 编译固件

```bash
cd firmware
./build.sh          # Windows 用 Git Bash 执行；Linux/macOS 直接执行
```

若交叉编译器不在默认路径，先设置环境变量：

```bash
export ARMGCC_HOME="C:/Users/lenovo/.workbuddy/binaries/armtc/gcc-arm-none-eabi-10.3-2021.10"
```

产物在 `firmware/build/`：`fw.elf`（调试）、`fw.hex`（ST-Link Utility / FlyMcu）、`fw.bin`（st-flash / OpenOCD）。

当前编译结果：

```
FLASH:  8836 B  / 64 KB   (13.5%)
RAM:    2200 B  / 20 KB   (10.7%)
```

### 2. 烧录

```bash
# st-flash（推荐）
st-flash write build/fw.bin 0x08000000

# 或者 OpenOCD
openocd -f interface/stlink.cfg -f target/stm32f1x.cfg \
        -c "program build/fw.elf verify reset exit"
```

也可以用 STM32CubeProgrammer 图形界面烧 `fw.hex`。

### 3. 运行上位机

```bash
cd host
pip install pyserial          # 唯一依赖

python monitor.py --list      # 看看串口号是多少
python monitor.py --port COM3 # Windows 示例
python monitor.py --port /dev/ttyUSB0   # Linux 示例
```

然后浏览器打开 \*\*<http://127.0.0.1:8080\*\*。>

### 4. 没硬件也能演示

```bash
python monitor.py --sim
```

模拟模式会生成一段"手持晃动"的运动数据，**并且按与固件完全相同的协议组帧、  
再完整走一遍解析流程** —— 验证的是整条协议栈，不是假造的界面动画。  
面试前用它把界面和讲解流程跑熟，板子到了再切真机。

## 四、通信协议

帧格式（小端序）：

```
┌──────┬──────┬──────┬──────┬────────┬──────────┬─────────┬──────┐
│ 0xAA │ 0x55 │ TYPE │ LEN  │ SEQ(2) │ TICK(4)  │ PAYLOAD │ CRC8 │
└──────┴──────┴──────┴──────┴────────┴──────────┴─────────┴──────┘
   帧头    帧头    类型   长度   帧序号  时间戳ms     数据     校验
```

- `TYPE`：`0x01` 数据帧、`0x02` 状态帧、`0x03` 日志帧
- `CRC8`：多项式 `0x07`，初值 `0x00`，覆盖 TYPE 到 PAYLOAD 共 `8+LEN` 字节
- 数据帧 payload（28 字节）：

| 字段        | 类型        | 说明                             |
| --------- | --------- | ------------------------------ |
| accel[3]  | int16 ×3  | 已扣零偏，±8g → 4096 LSB/g          |
| gyro[3]   | int16 ×3  | 已扣零偏，±2000°/s → 16.4 LSB/(°/s) |
| mpu_temp  | int16     | MPU6050 片内温度 ×10               |
| angle[3]  | int16 ×3  | roll/pitch/yaw ×100（度）         |
| adc[3]    | uint16 ×3 | 外部0 / 外部1 / 内部温度原始值            |
| chip_temp | int16     | STM32 内部温度 ×10                 |

上位机可下发命令（单字节）：`C` 重新校准、`V` 请求状态、`S` 暂停/继续上传、`R` 复位统计。

协议在 C（`firmware/src/protocol.c`）和 Python（`host/protocol.py`）两端各实现一份，  
Python 端带自检用例：

```bash
python protocol.py --selftest
```

覆盖：CRC8 标准向量、组帧往返、物理量换算、断帧续接、粘包、CRC 错误检测、状态帧。

## 六、几个值得在面试里讲的设计决策

1. **为什么不用硬件 I2C？**  
   STM32F1 的 I2C 外设在总线被从机拉低时容易进入 BUSY 死锁，需要复位外设甚至断电。  
   软件 I2C 虽然占用 CPU，但可以实现"9 个时钟脉冲 + STOP"的总线恢复，  
   任何异常都能自愈。本项目在连续 50 次通信失败后会自动恢复总线并重新初始化传感器。
2. **为什么发送要用 DMA？**  
   100Hz × 39 字节的数据流如果用 CPU 逐字节轮询发送，会长时间占用主循环。  
   DMA 发送只需要在启动前填好缓冲区，传输过程 CPU 完全空闲。  
   并且做了流量控制：上一帧没发完就直接丢弃并计数，绝不让串口把采样循环拖垮。
3. **为什么中断里只置标志？**  
   I2C 突发读 14 字节需要约 0.7ms，如果在 TIM2 中断里做，会阻塞 SysTick 和串口接收。  
   现在中断只做"置标志 + 计数"，实际采样在主循环完成，  
   并且用 `overrun` 计数器量化"主循环有没有跟上"这件事。
4. **为什么外部晶振失败要不死机等？**  
   部分廉价最小系统板的 8MHz 晶振未焊接或虚焊。如果代码里死等 `HSERDY`，  
   板子就会表现为"下载成功但没反应"，排查起来很痛苦。  
   这里做了超时判断，失败自动切 HSI（64MHz），程序照样跑，  
   上位机状态帧里能看到实际主频是多少。
5. **yaw 一定会漂移，这不是 bug。**  
   六轴方案没有磁力计提供绝对航向参考，yaw 只能靠陀螺仪积分，零偏积分后必然发散。  
   加速度只能提供 roll/pitch 的长期参考（重力方向），提供不了 yaw 的。  
   要解决需要加磁力计做九轴融合，或者换更接近的方案。
